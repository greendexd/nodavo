# Nodavo для Windows

[English](README.md) · [Русский](README.ru.md)

В этом каталоге находится первая нативная оболочка Nodavo на WinUI 3. В ней есть двуязычные разделы обзора, устройств, расположения, передач и настроек. Обзор сохраняет phase соединения, peer, input owner и точное состояние фокуса, отдельно показывая доступность взаимно аутентифицированного агента, готовность локального ввода, локальные дисплеи и синхронизацию peer-топологии. На нём также есть защищённые условиями ручные действия получения/возврата фокуса с видимой ограниченной сверкой. Экран устройств реализует ожидающее/ручное сопряжение, сравнение и подтверждение кода, ограниченный список доверенных устройств, транзакционные изменения всех четырёх локальных разрешений и подтверждаемый разрушительный отзыв. Экран расположения загружает ту же ограниченную авторитетную сводку доверия и позволяет назначить активному peer ровно одно из значений `disabled`, `left`, `right`, `above` или `below` без оптимистического состояния и слепого повтора. Передачи принимают только результаты явного выбора файлов/папок системными Windows picker, до IPC применяют локальные пределы 32 путей и 4 КиБ на путь, а в ленте текущих/недавних передач показывают только скрытые идентификаторы, прогресс в байтах и разрешённую агентом отмену. Это заявления об исходниках и CI, а не о квалифицированном Windows runtime.

Platform source Windows теперь владеет одним process-wide per-monitor-v2 display service. Скрытое broadcast-capable window сокращает задержку обнаружения, а authoritative источником остаются ограниченный full polling и два одинаковых DisplayConfig-backed samples. Capture и injection используют один snapshot и непереиспользуемые opaque identities; routing enable, доставка suppressed reliable Raw Input, absolute injection, stop/restart и timed-detach poison сериализованы с invalidation. Агент quiesce’ит старую lease и требует acknowledgement точной replacement topology, когда локальный graph публикуется для inbound control; outbound-only operation намеренно сохраняет этот graph unpublished. Portable и Windows cross-target checks покрывают эти contracts, но физические x64/ARM64 hot-plug, RDP, mixed-DPI, lock/UAC и suspend/resume остаются Windows runtime gates.

## Поддерживаемые цели исходного проекта

- Windows 10 22H2 и Windows 11.
- Конфигурации x64 и ARM64.
- Упакованные тестовые сборки MSIX и неупакованные тестовые сборки.
- Работа только в сеансе текущего пользователя. Манифест запрашивает `asInvoker`; экран входа, защищённый рабочий стол UAC, Session 0 и привилегированное управление без присутствия пользователя не поддерживаются.

## Сборка на Windows

Установите Visual Studio 2022 версии 17.10 или новее с workload для разработки Windows-приложений, .NET 8 SDK, Windows 10/11 SDK 10.0.26100 и инструменты MSIX. Затем выполните из корня репозитория:

```powershell
dotnet restore apps/windows/Nodavo.Windows.sln -p:Platform=x64
dotnet build apps/windows/Nodavo.Windows.sln -c Release -p:Platform=x64
```

Для неупакованной тестовой сборки:

```powershell
dotnet build apps/windows/Nodavo.Windows.sln -c Release -p:Platform=x64 -p:NodavoPackageMode=Unpackaged
```

Кроссплатформенная статическая safety-проверка проверяет двуязычные ресурсы, XAML XML, порядок IPC-тайм-аутов, раздельное владение операциями доверия/расположения/передач, точное декодирование и сверку расположения, строгий ограниченный decoder передач, признаки polling/сверки, accessibility authority и блокировку повтора неоднозначных операций:

```bash
python3 apps/windows/tests/check_product_ui.py
```

Используйте `ARM64` и `win-arm64` для прямой нативной сборки на Windows ARM64. Workflow упаковки может cross-build этот payload на x64 Windows runner, но квалифицировать его runtime можно только на настоящем ARM64-устройстве. Добавленные publish-профили предназначены для разработки, а не для подписанного релиза.

Для запуска неупакованной сборки требуется соответствующий Windows App Runtime. Для публичного устанавливаемого MSIX нужны настоящая издательская идентификация и сертификат Authenticode; в репозитории их нет.

## Упаковка MSIX для x64 и ARM64

Скрипт упаковки собирает self-contained WinUI и Rust agent для x64 и ARM64, создаёт MSIX для каждой архитектуры, объединяет их в bundle, проверяет манифест и архитектуры PE и запрещает файлы приватных ключей внутри пакета. Он не устанавливает службу и не запрашивает повышение прав: Win32-манифесты остаются `asInvoker`, пакет работает на `mediumIL`, установка выполняется для текущего пользователя, а управление экраном входа/UAC secure desktop/Session 0 остаётся исключённым.

Для явно помеченного самоподписанного тестового артефакта на Windows:

```powershell
pwsh -NoProfile -File scripts/package-windows.ps1 `
  -Development -Version 0.1.0 -BuildNumber 1
```

Результат появится в `target/windows-packages/0.1.0.1-development/`. И имя bundle, и содержимое пакета содержат пометку `DEVELOPMENT-NOT-FOR-DISTRIBUTION`. Скрипт создаёт краткосрочный сертификат, проверяет подпись с временным доверием к нему, экспортирует только публичный `.cer` и удаляет приватный ключ из хранилища сертификатов. Для App Installer тестовый сертификат требуется в machine-wide хранилище `TrustedPeople`, что запрашивает подтверждение администратора, хотя сам MSIX устанавливается для текущего пользователя. Делайте это только на отдельной тестовой машине и удаляйте сертификат после проверки.

Release-режим намеренно работает fail-closed. Он требует все перечисленные переменные окружения и отказывается собирать пакет, если хотя бы одна отсутствует или не согласована:

- `WINDOWS_PACKAGE_PUBLISHER`: точный X.509 subject, записываемый в манифест пакета.
- `WINDOWS_PACKAGE_FAMILY_NAME`: точный зарезервированный PFN; официальный Windows API package identity должен вывести его из настроенных имени пакета и publisher.
- `WINDOWS_PUBLISHER_DISPLAY_NAME`: публичное имя издателя.
- `WINDOWS_SIGNING_PFX`: путь к identity-validated Authenticode PFX.
- `WINDOWS_SIGNING_CERTIFICATE`: публичный DER-сертификат, совпадающий с PFX. Во время сборок Rust и .NET доступны только этот публичный сертификат и его хэш.
- `WINDOWS_SIGNING_PFX_PASSWORD`: пароль PFX. Скрипт копирует его в `SecureString` и удаляет переменную окружения процесса до запуска Rust, .NET и других инструментов сборки; пароль не передаётся SignTool в командной строке.
- `WINDOWS_TIMESTAMP_URL`: HTTPS endpoint RFC 3161 timestamp.
- `WINDOWS_SIGNING_CHAIN_ALLOWLIST`: разделённый запятыми или точками с запятой allowlist проверенных 40-символьных hex-thumbprint сертификатов. Непосредственный issuing CA или корневой сертификат проверенной цепочки должен совпасть с одной записью; одного thumbprint подписывающего leaf недостаточно.

```powershell
pwsh -NoProfile -File scripts/package-windows.ps1 `
  -Version 1.0.0 -BuildNumber 1
```

До сборки release-путь проверяет публичный сертификат, точный PFN, online revocation, доверенную цепочку, subject, срок действия и Code Signing EKU. PFX с приватным ключом не открывается и не импортируется до завершения всех сборок Rust и .NET, должен содержать точный публичный сертификат и очищается только по точным известным thumbprint импортированных сертификатов. Каждый `Nodavo.Windows.exe`, каждый `agent\nodavo-agent.exe` и итоговый bundle получают одну и ту же доверенную подпись с RFC 3161 timestamp. После распаковки скрипт повторно проверяет точные identity/PFN/AUMID/executables, подписанта, встроенную server-auth policy UI, x64/ARM64 payload, multiset из двух capabilities, отсутствие development-маркера и секретных файлов. Сертификат и пароль релиза не сохраняются ни в репозитории, ни в артефакте.

Пакет объявляет только доступ к LAN (`privateNetworkClientServer`) и capability `runFullTrust`, необходимую desktop-пакету `mediumIL`. Он не запрашивает broad filesystem, location, camera, microphone, enterprise authentication, службу, UAC или secure desktop. Включённый `app.manifest` явно запрашивает `asInvoker` с `uiAccess=false`.

Отдельный workflow упаковки Windows доказывает только способность self-signed development-пути собрать и проверить x64/ARM64 bundle на Windows runner. Срок хранения такого артефакта короткий, а в имени указано, что он не предназначен для распространения. У workflow нет release credentials, и он не может создать релиз.

## Контракт локального IPC

До декодирования любого frame агент связывает принятое соединение pipe с непрозрачным guard, который удерживает точные handles клиентского процесса, primary token и executable. Авторизация требует настроенные development- или release-identity пакета, PFN, AUMID UI, расположение executable и встроенный сертификат подписанта Authenticode. Guard повторно проверяет те же identity процесса/token/package/image и перед каждым ограниченным чтением, и после декодирования непосредственно перед dispatch.

UI независимо аутентифицирует pipe server до записи команды. Его compile-time policy должна совпадать с точными name, publisher, PFN, AUMID UI и корнем установленного пакета из `Package.Current`. Затем UI удерживает процесс сервера, о котором сообщил pipe, его primary token, время создания и read-only no-share-delete handle точного обычного файла без reparse point `agent\nodavo-agent.exe` под этим корнем. Сервер должен иметь те же identity пользователя/сеанса/logon, оставаться живым, исполнять этот точный image и иметь закреплённого доверенного подписанта Authenticode; release-сборка дополнительно требует проверенное timestamp evidence. UI повторно проверяет соединение и удерживаемую identity перед ожиданием ответа и после ограниченного чтения ответа, до JSON-декодирования. Для отдельно запускаемого процесса agent не заявляются package identity или AUMID; доверие основано на content-enforced корне аутентифицированного пакета UI и точном подписанном executable внутри него. Ненастроенные и unpackaged-сборки UI работают fail closed; runtime-обходов через environment или подменяемый path нет.

Вместе эти проверки отклоняют обычные независимые клиенты того же пользователя/сеанса, захват имени pipe и подмену PID, path, package, token, executable или подписанта. Они не создают отдельный Windows principal между двумя процессами `mediumIL` и не заявляют защиту от произвольного malware того же пользователя. Процесс, получивший инвазивный доступ к одному из авторизованных процессов — например `PROCESS_DUP_HANDLE`, чтение/запись памяти процесса, debugging, injection или hollowing, — считается скомпрометировавшим этот процесс и находится вне границы Windows 1.0. Для более сильной threat model потребуется отдельно изолированный broker/principal; более короткие соединения «один запрос — один ответ» уменьшают lifetime capability, но не заменяют такую изоляцию.

Интерфейс подключается к `\\.\pipe\nodavo-agent-{SID-текущего-пользователя}` с опцией .NET, разрешающей именованный канал только текущему пользователю. Каждое аутентифицированное соединение переносит ровно один запрос и один ответ, после чего закрывается; для следующей команды создаётся новое аутентифицированное соединение. Каждое сообщение состоит из четырёхбайтовой беззнаковой длины в big-endian и UTF-8 JSON; жёсткий предел — 64 КиБ. Оболочка отправляет ограниченные команды статуса, аварийного отключения, сопряжения, списка доверенных устройств, изменения разрешений, отзыва, admission выбранных путей, списка и отмены передач. У долгих запросов сопряжения есть ограниченный тайм-аут и отмена из интерфейса. Все разрешения по умолчанию выключены, а явный выбор подписывается в доверии сопряжения. У обновления списка доверия и мутации доверия раздельное сериализованное владение. Переключатель разрешения сохраняется после точного echo; явная ошибка агента возвращает предыдущее авторитетное значение. Потерянный, просроченный или некорректный ответ мутации вместо этого считается неизвестным: элементы устройства остаются отключены, пока UI ждёт дольше двух последовательных пятисекундных safety-окон агента и сверяется с новым авторитетным списком доверия.

Теперь каждая запись доверенного peer обязана содержать ровно одно расположение из пятизначного enum без неизвестных или повторных полей. Экран расположения отправляет одну точную команду `set_peer_placement` с отдельным 15-секундным deadline мутации и принимает только подтверждение `peer_placement_changed`, повторяющее точный peer и запрошенное расположение. Видимое текущее расположение не меняется оптимистически. Любая явная ошибка агента, тайм-аут, потеря соединения, некорректный ответ или несовпадающий echo считается неоднозначным, потому что сохранённое состояние уже может быть авторитетным; оболочка блокирует только этот peer и вызывает `list_trusted_peers`, не повторяя мутацию. Успешный аутентифицированный список применяет фактическое расположение, состояние revocation или отсутствие peer и снимает неопределённость; неудачный список оставляет именно этот peer заблокированным до успешного последующего явного обновления. Другие активные peer снова доступны после окончания ограниченной операции. Отозванные peer и все элементы, которыми владеет выполняющийся запрос, отключены.

Запрос файла содержит от одного до 32 уникальных абсолютных путей, явно возвращённых Windows picker; каждый путь в UTF-8 не превышает 4 КиБ, а немедленный ответ о локальном admission сокращается до скрытого ID передачи до попадания во view. Если это подтверждение потеряно или некорректно, существующий выбор блокируется от повтора до нового явного выбора через picker. Успешный или неоднозначный admission запускает до пяти последовательных попыток получить авторитетный список; временные и явные protocol errors сохраняют это состояние сверки. После окончания попыток кнопка «Обновить передачи» может запустить ещё одно ограниченное окно проверки только состояния и никогда не отправляет выбранные объекты повторно. Запросы списка и отмены передач имеют отдельные восьмисекундные тайм-ауты и используют новый взаимно аутентифицированный pipe. Строгий decoder принимает не более 160 уникальных канонических ненулевых UUID, ограниченные 10 ГиБ счётчики, точные enum направления/фазы/ошибки и не допускает отсутствующих, повторяющихся, неизвестных, лишних или приватных полей. Загруженный экран передач последовательно опрашивает агент примерно раз в секунду, только пока есть незавершённая строка, незаконченная сверка отмены или ограниченная сверка admission. Новый instance агента очищает session feed в памяти, устаревшие revision игнорируются, неудачный poll сохраняет строки с предупреждением об устаревании, а сокращённый ответ явно помечается. Отмена доступна только когда агент пометил точную строку cancellable; мутацией одновременно владеет одна строка, а после неоднозначного ответа опрашивать или повторять отмену можно только для того же ID, пока все остальные строки заблокированы. Это владение заканчивается только при evidence `cancel_requested`/terminal-фазы, явном детерминированном отказе, новом instance агента или авторитетном отсутствии ID в несокращённом списке; одно присутствие в равной revision никогда его не снимает. Единственные terminal-фазы — `completed`, `cancelled` и `failed`; равенство байтов не означает завершение, а передача нулевого размера остаётся indeterminate до явной terminal-фазы. Недавние строки — только наблюдения в памяти текущего сеанса агента, а не постоянная история. Оболочка не записывает в журнал тела ответов, трафик устройств, ввод, буфер, имена файлов, полные ID передач, коды сопряжения, ключи и постоянные сетевые идентификаторы.

## Готовность

Status decoder требует ровно `event`, `phase`, `connected_peer`, `input_owner`, `focus_state` и точный readiness object из четырёх полей. Отсутствующие, повторяющиеся, неизвестные, повреждённые, private или не-Windows Accessibility values отклоняются до обновления UI. Error envelopes также требуют ровно `event`, `code` и bounded `message`; malformed или unknown errors не могут стать deterministic focus rejection. Ввод, локальные дисплеи и peer topology остаются независимыми: доступный монитор не означает, что аутентифицированный peer layout синхронизирован. Заблокированный input desktop показывает только рекомендацию разблокировать ПК или вернуться к обычному desktop и обновить статус; shell не предоставляет Accessibility action, UAC request, elevation или обход secure desktop. Неудачный status или emergency operation очищает stale readiness, peer и input owner. Обычный status ждёт восемь секунд: это включает трёхсекундный agent probe и overhead аутентифицированного IPC. Emergency stop использует отдельный client deadline 25 секунд, превышающий единый 20-секундный fail-closed safety budget агента. Для этого пути есть source/static tests и Windows CI compilation, но installed x64/ARM64 desktop transitions остаются physical runtime gate.

Decoder также требует ровно один `focus_state` с одним из трёх ограниченных значений: `local`, `controlling_peer` или `controlled_by_peer`; отсутствие, повтор или неизвестное значение приводит к fail-closed. Ручное получение разрешено только при точном local state, подключённом peer, phase `connected`, готовом вводе, доступной local topology и готовой session topology. Возврат остаётся доступным для обоих точных nonlocal states даже при ухудшении readiness. Получение отправляет один `request_remote_focus` с фиксированным `ttl_ms=5000`; возврат отправляет один `release_focus` со своим 15-секундным request deadline. Ни один mutation не повторяется. Local response на получение или неоднозначный результат получения ожидает полное пятисекундное окно lease и выполняет одну свежую status-only сверку. Точный local response на возврат завершает действие немедленно; неоднозначный возврат выполняет одну status-only сверку. Весь путь mutation, ожидания и сверки использует общий deadline 30 секунд, после которого элементы фокуса остаются заблокированы с неизвестным владением до успешного последующего явного обновления статуса. Emergency stop никогда не отключается, отменяет устаревший focus workflow и увеличивает generation, поэтому поздние ответы не меняют отображение. Это покрытие исходниками, статическими проверками и reducer-тестами; физическое переключение фокуса между подписанными Windows-пакетами x64/ARM64 и настоящим macOS peer остаётся runtime release gate.

## Lifecycle агента из пакета

Экран обзора может запустить непривилегированный `agent\nodavo-agent.exe` из пакета только после явного действия «Запустить агент». Lifecycle coordinator сначала проверяет приватный pipe, сериализует параллельные запросы и запускает процесс не более одного раза перед ограниченным ожиданием готовности. Если sign-in activation одновременно срабатывает с действием UI, first-instance pipe агента заставляет более поздний процесс завершиться fail closed вместо создания второго сервера. UI использует только `Package.Current.InstalledLocation`, требует каноническое нахождение внутри корня пакета, точное имя файла и обычный файл без reparse point, затем напрямую создаёт процесс с `UseShellExecute=false`, `CreateNoWindow=true`, без аргументов и недоверенного ввода executable. Возвращённый process handle сразу освобождается без завершения дочернего процесса. Дизайн полагается на неизменность и content enforcement установленного корня пакета со стороны Windows; запасного unpackaged-пути нет.

Пакет также объявляет одну `windows.startupTask` для этого точного executable агента с `Enabled=false`. Экран настроек — единственное действие внутри приложения для включения и выключения. Он показывает состояния enabled, disabled, disabled-by-user, disabled-by-policy, enabled-by-policy и unavailable; приложение не отменяет выбор пользователя в Task Manager/Startup Apps и политику администратора. Запасных вариантов через service, elevation, scheduled task, Registry `Run`, shell или PowerShell нет. Startup остаётся пользовательским и выполняется только после входа, но не на экране входа, защищённом рабочем столе UAC или в Session 0. Для напрямую созданного дочернего процесса не заявляется отдельный packaged activation identity; текущему агенту требуется только непривилегированное поведение в интерактивном сеансе пользователя.

Тесты reducer, параллельного запуска, отмены и ограниченного тайм-аута подключены к Windows CI на уровне исходников. Запуск установленного MSIX и поведение при входе всё ещё требуют runtime-квалификации на настоящих x64 и ARM64 и не заявляются на основании одной компиляции исходников или CI. Происхождение дизайна ограничено документацией Microsoft для [`StartupTask`](https://learn.microsoft.com/uwp/api/windows.applicationmodel.startuptask), [startup extensions packaged desktop](https://learn.microsoft.com/windows/apps/desktop/modernize/desktop-to-uwp-extensions), [`Package.InstalledLocation`](https://learn.microsoft.com/uwp/api/windows.applicationmodel.package.installedlocation) и прямого [`ProcessStartInfo.UseShellExecute=false`](https://learn.microsoft.com/dotnet/api/system.diagnostics.processstartinfo.useshellexecute).

Windows updater source теперь содержит production-inert boundary staging и inspection. Он принимает только canonical fixed-volume namespace, удерживает no-delete handles для каждого проверенного directory component, требует точный owner/current-user DACL, использует межпроцессную lease, ограниченные content-addressed names, exact offsets, quotas и retention и выполняет seal только синхронизированных файлов. Appx bundle/package inspection читает из уже retained file handle через ограниченный read-only stream и никогда повторно не открывает untrusted pathname. Этот source не выполняет deployment, registration, activation, launch или rollback package, не подключён к WinUI update screen и всё ещё требует реальных x64/ARM64 DACL/share/durability/Appx runtime tests.

## Текущие ограничения

На текущем macOS-компьютере исходники нельзя компилировать, линковать или запускать под Windows. WinUI x64 compile-проверяется в Windows CI, а обязательным свидетельством сборки полного development bundle x64/ARM64 служит workflow упаковки. CI остаётся подтверждением компиляции/упаковки, но не интерактивного runtime.

В исходниках Rust теперь есть connection-bound guard package, process/token, executable и подписанта Authenticode в дополнение к проверкам того же пользователя/сеанса и защищённому DPAPI-хранилищу идентификаторов/доверия. В этой оболочке есть соответствующие сценарии сопряжения, управления доверием, точного редактирования расположения для каждого peer, явного admission передачи, ограниченного decoding progress/session feed, сверки отмены, on-demand запуска из пакета и opt-in startup task. Они компилируются или проходят проверки исходников/XML, но ещё не запускались вместе на квалифицированных настоящих Windows x64 и ARM64, поэтому успешный runtime не заявляется. Экран передачи не доказывает сквозную доставку, постоянную историю или поддержку resume. Установленный lifecycle/autostart, физическое поведение расположения/маршрутизации, UX буфера, UX resume передачи, трей, диагностика, updater UI/activation и production signing остаются неквалифицированными или ещё разрабатываются. `Package.appxmanifest` предназначен только для разработки и использует отдельный identity, поэтому его нельзя перепутать с публичным релизом или обновить им релиз.

Оставшиеся release gates точны и требуют внешней инфраструктуры: зарезервировать и зафиксировать окончательные Store package identity и publisher в Partner Center; получить Store approval для `runFullTrust` либо использовать identity-validated сертификат прямой дистрибуции; настроить защищённые signing credentials и надёжный endpoint RFC 3161; выполнить матрицы чистой установки, обновления, запрета downgrade, удаления, истечения сертификата, tamper, rollback и реального runtime x64/ARM64; опубликовать стабильные HTTPS-артефакты и хэши до создания WinGet manifest. MSI не создаётся, потому что Nodavo ещё не обосновал вторую технологию установки, не проверил её per-user upgrade/uninstall semantics и не квалифицировал WiX/MSI toolchain. MSI и portable ZIP остаются опциональными решениями, а не заявленными релизами.

Происхождение дизайна упаковки ограничено собственными требованиями Nodavo и официальной документацией Microsoft по [автоматизации single-project MSIX](https://learn.microsoft.com/windows/apps/windows-app-sdk/single-project-msix), [package identity](https://learn.microsoft.com/windows/apps/desktop/modernize/package-identity-overview), [capabilities desktop-пакета](https://learn.microsoft.com/windows/apps/package-and-deploy/app-capability-declarations) и [подписи/timestamp MSIX](https://learn.microsoft.com/windows/msix/package/signing-package-overview). Исходники и ресурсы установщиков сторонних KVM-продуктов не использовались.

Интерфейс и IPC-код — оригинальная clean-room разработка на основе собственной архитектуры и контракта локального IPC Nodavo; исходники и ресурсы сторонних KVM-продуктов не использовались.
